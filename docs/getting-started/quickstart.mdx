**Tardigrade** is a TypeScript framework for building durable, modular agents around an immutable event log. By the end of this guide, you will know how to run a Tardigrade agent locally, inspect its trajectory, and deploy it to the cloud.

### Prerequisites

1. [Bun](https://bun.sh/docs) 1.4 or above
2. The latest [Tardie CLI](/docs/cli)
3. An LLM API key from a provider of your choice

For the fastest setup, create an [OpenRouter API key](https://openrouter.ai/settings/keys) before you begin. For deployment, install either the [Wrangler CLI](https://developers.cloudflare.com/workers/wrangler/install-and-update/) for Cloudflare or the [Celld CLI](https://celld.dev/docs/) for your own cloud.

### Initialize your project

First, install the [Tardie CLI](/docs/cli).

```bash variant="single"
bun add -g tardie@latest
```

Now, use the [Tardie CLI](/docs/cli) to create a new `tardie-agent` directory and configure a language model provider.

```bash variant="single"
tdg init tardie-agent --template quickstart
```

After the setup, you should see the following files:

<Filesystem root="tardie-agent/">
  - `actor.ts` Actor and components
  - `server.ts` Bun server entry
  - `worker.ts` Cloudflare and Celld Worker entry
  - `wrangler.jsonc` Cloudflare Worker configuration
  - `celld.jsonc` Self-hosted Celld configuration
  - `models.lock.json` Resolved deployment model scope
  - `migrations/0001_catalog.sql` Model catalog database schema
  - `package.json` Dependencies and module metadata
</Filesystem>

Move into the new project directory:

```bash variant="single"
cd tardie-agent
```

### Define your first actor

#### Hello world!

For this Quickstart, we'll implement a simple agent with a tool that returns dummy weather data for a given city. In another guide, we'll explore a more advanced setup by building an agent that can execute JavaScript code, call MCP servers, and run subagents within a sandbox.

As you follow along, you will see tip boxes that you can expand to learn what happens behind the scenes.

<Tip title="About these tips">
These notes explain what Tardigrade is doing behind the scenes. You can skip them and still complete the guide.
</Tip>

Within `actor.ts`, you will see the following code:

```ts expanded
import { Effect } from "effect"
import { actor } from "tardie/core"
import { agentMessageMethod, infer, outputValidateOnce, system, tool } from "tardie/agent"

const actorName = "tardie-agent"

const actorInstructions = `
Answer questions about the weather.
Use the weather tool for current conditions.
`.trim()

const weather = tool({
  spec: {
    name: "get_weather",
    description: "Get the current weather for a city",
    inputSchema: { type: "object", properties: {}, additionalProperties: false }
  },
  run: () => Effect.succeed({ temperature: 21 })
})

export default actor({
  name: actorName,
  methods: { message: agentMessageMethod },
  components: [infer([
    system(actorInstructions),
    weather,
    outputValidateOnce
  ])]
})
```

<Tip title="About actor components">
A Tardigrade component has the following interface:

```ts
interface ComponentDefinition<State, View, Requirements = never> {
  readonly name: string
  readonly initial: () => State
  readonly step: (state: State, event: Event, context: TransitionContext) => State
  readonly output: (state: State) => {
    readonly view: View
    readonly transitions: ReadonlyArray<Transition<never, Requirements>>
  }
  readonly cancelState?: (
    state: State,
    cancellation: InvocationCancellation
  ) => ReadonlyArray<Transition<never, Requirements>>
  readonly children?: ReadonlyArray<Component<unknown, unknown>>
}
```

`initial` creates private component state. `step` folds each event into that state. `output` derives the component's view and enabled transitions. Use the context passed to `step` to declare tagged intents and effects; retain them in state until their completion is observed. When components are composed, Tardigrade combines their views and reconciles their transitions. The `Requirements` type records the Effect services needed to execute those transitions.

The `weather` component contributes `get_weather` to the agent's view and keeps its specification beside its Effect handler:

```ts
const weather = tool({
  spec: {
    name: "get_weather",
    description: "Get the current weather for a city",
    inputSchema: { type: "object", properties: {}, additionalProperties: false }
  },
  run: () => Effect.succeed({ temperature: 21 })
})
```

Tardigrade records each model response as `ModelReturned`, which carries its usage. When the model selects `get_weather`, Tardigrade also records `ToolCalled`, linked to the response by `responseId`. The inference component finds the handler in the current view, runs its Effect, and records `ToolReturned`. The next model request includes the result.

A model response can request several tools. Tardigrade records every call before dispatch, runs native tools concurrently by default, and waits for every result before the next model request. Each call has its own result. The response contributes usage once. Replay reuses committed results and retries unfinished work.

`DEFAULT_TOOL_CONCURRENCY` is `"unbounded"`. Set `infer(components, { toolConcurrency: 4 })` to admit at most four pending calls at a time. Additional calls wait in recorded order. Set `concurrency: 1` on a native tool binding to serialize calls to that tool. These limits appear in the model instructions or tool description.

Code mode defaults to `DEFAULT_CODE_TOOL_CONCURRENCY`, which is `1`. Set `codeMode(components, { toolConcurrency })` to control admission of `execute` calls. Code execution follows the code scheduler. Custom model integrations supply Effect's `LanguageModel` service. The inference component translates its stream into response evidence and tool requests. The interpreter records those requests before tool execution.
</Tip>

### Running it locally

Run the generated Bun API server directly:

```bash variant="single"
bun run dev
```

The server runs on `localhost:4242` by default. Check `curl localhost:4242/healthz` from another shell to confirm it is ready. Edit `server.ts` to change how the actor and API are assembled.

### Send your first message

Once you have the agent running, create a root thread named `quickstart`, then send it your first message. The creation command prints the assigned thread ID.

```bash
tdg thread create --name quickstart
tdg call message '{"text":"What is the weather in Singapore?"}' --thread quickstart
```

<Tip title="About actor methods">
The actor code defines the following method:

```ts highlight="3"
export default actor({
  name: actorName,
  methods: { message: agentMessageMethod },
  components: [infer([
    system(actorInstructions),
    weather,
    outputValidateOnce
  ])]
})
```

An actor method defines a typed, durable call boundary. Its input and output schemas validate the public API, its event function records the call, and its projection derives the current call state from events. A method can also define how cancellation is recorded.

```ts
const AgentMessageInput = Schema.Struct({
  text: Schema.String,
  input: Schema.optionalKey(Schema.Unknown),
  model: Schema.optionalKey(ModelRef)
})

const agentMessageMethod = actorMethod({
  input: AgentMessageInput,
  output: Schema.String,
  event,
  projection,
  cancellation: { event: cancellationEvent }
})
```

Each `message` call remains pending until the method projection observes a completed, failed, or cancelled turn. The Quickstart command appends `MessageReceived`, and a later `TurnCompleted` resolves the call with its string output.
</Tip>

### Inspecting the actor logs

After your call, you will see `.tardigrade/data/`. This directory holds one SQLite database for each actor instance. An event log is an immutable, append-only ledger of events sent to the actor and events generated by the actor.

<Filesystem root=".tardigrade/data/">
  - `<actor-instance>.sqlite` Registry for the `main` actor instance
  - `<actor-instance>.sqlite.threads/`
    - `<thread>.sqlite` Event log for the `quickstart` thread
</Filesystem>

A simplified view of the message includes the following events. The log also records the model requests and responses.

<EventLog>
  1. `ThreadCreated` `{ address: { ... } }`
  2. `MessageReceived` `{ text: "What is the weather..." }`
  3. `ToolCalled` `{ name: "get_weather", arguments: { ... } }`
  4. `ToolReturned` `{ result: { ... } }`
  5. `TurnCompleted` `{ output: "..." }`
</EventLog>

These events persist across runs. Each thread has a separate SQLite event database in the `.sqlite.threads/` directory beside its actor instance database. Instance database filenames encode the JSON pair `[actor, instance]` as base64url. Thread database filenames encode the thread ID as base64url. Set `TARDIGRADE_ACTOR_DATA` to change the storage directory.

You can use the following command to view the events:

```bash variant="single"
tdg events <thread>
```

If you used the command in this guide, the first message landed in a thread called `quickstart`. To view its events, run:

```bash variant="single"
tdg events quickstart
```

### Send a follow up message

To send a follow up message, simply send another message to the same thread:

```bash variant="single"
tdg call message '{"text":"How about San Francisco?"}' --thread quickstart
```

### Deploy your agent

Before the first Cloudflare deployment, follow the [Cloudflare setup guide](/docs/platforms/cloudflare#configure) to create the catalog database, apply its migration, and set secrets. Then deploy the agent:

```bash variant="single"
bun run deploy:cloudflare
```

To deploy it on your own cloud, use Celld:

```bash variant="single"
bun run deploy:celld
```

### Send a message to your cloud agent

Once your deployment is ready, create a root thread on the remote host, then invoke its message method. Set `ACTOR_URL` to your deployment URL.

```bash
tdg thread create --name quickstart --url "$ACTOR_URL"
tdg call message '{"text":"What is the weather in Singapore?"}' --thread quickstart --url "$ACTOR_URL"
```
