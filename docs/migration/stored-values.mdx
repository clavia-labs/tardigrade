Native Bun and Cloudflare journals store immutable Grove documents alongside an append-only event log. Core owns replay, reducers and effect lifetimes. Grove owns document representation, validation, synchronous reads, retention and collection. Journal records, document dependencies, ownership and SQL recovery bookkeeping share a native SQLite transaction.

## Storage compatibility

`bunJournal`, `createBunHost` and `cloudflareJournal` use the native stored-value journal. They reject retained data in the legacy event, checkpoint, tree-checkpoint or accepted-input tables before admitting writes. Cloudflare hosts also reject legacy KV scheduler and watchdog data. These checks preserve the source data; the native factories provide no automatic conversion.

Use a separate destination database or Durable Object for state transfer. Stop source writes at a settled boundary, extract application JSON with the source version, convert it to the destination atoms' state codecs, and create a destination thread with `initialState`. The [state initialisation guide](/docs/migration/state-initialisation) describes this flow. Pending effects, replies and recovery records require an application-specific migration. Raw Grove references cannot transfer state between storage scopes; materialize the source value and import JSON into the destination.

A database cannot mix legacy and native journal data for the same actor. Bun observation supports either format and rejects a mixed actor database. A Bun host backup contains the native journal, Grove data, delivery receipts and SQL recovery tables together.

Grove writes node format 4 and can decode format-3 nodes. Its opaque reference codec has a separate format version and scope. Node decoding compatibility does not imply journal-layout compatibility.

## Document authoring and references

`durableAtom` selects schema-bound Grove documents automatically for a tagged root or a struct whose fields each declare `tree`, `appendOnly` or `keyValue`. `tree(schema)` supports localized edits. `keyValue(valueSchema)` supports whole-entry set and removal, with whole entry values stored as SQLite MVCC revision rows; retained snapshots preserve visible revisions and collection removes superseded rows. Untagged schemas retain plain value reducers and emit a deprecation warning at atom construction. Partially declared collection structs fail immediately. `appendOnly(ArraySchema)`, exported by Grove and Core, permits appends and whole-array replacement while rejecting edits inside existing entries and splices. Trajectory and rendered context entries use this marker; compaction replaces the context array as a whole. Its operations are `set`, `append`, `splice`, `remove` and `batch`; each successful edit returns an immutable document. Removal supports optional object fields and string-keyed record entries. Array deletion uses `splice`. Schemas with cross-field or collection-wide checks can require whole-value edits; unsupported selective operations fail explicitly. The [Grove API](https://github.com/clavia-labs/tardigrade/blob/main/packages/grove/README.md) describes these constraints.

Both standalone and SQLite Grove sessions require an explicit scope. A document's `reference` identifies its exact version within that scope. Documents have no public raw `root`, and document bindings accept opaque references when opening a version. The raw `Reference` schema and `selectionReference` helper are absent; `selectionValueReference` recognizes a selection as an opaque reference. Persist references with Grove's `encodeReference` and `decodeReference`. Core's `StateReference` validates this encoded form. A raw node hash is insufficient. Effect input selections contain `{ reference, target }`: Grove encodes the source path, range and per-item projection inside the reference, while `target` identifies where Core inserts the resolved value.

## Grove SQLite integration

`@tardie/grove/sqlite` exposes `makeSync(driver, options)` as its storage implementation. It accepts an explicit native synchronous driver and stable scope. Effect callers can wrap synchronous operations with `Effect.try`; transaction callbacks must still finish synchronously. The module has no Effect SQL `make`, `Grove` service, `layer` or borrowed `nativeLoader` API. The independent `grove_nodes`, `grove_chunks` and `grove_owners` layout requires explicit data transfer before using the `grove_value_*` store.

## Package exports

The supported Grove entry points are `@tardie/grove` and `@tardie/grove/sqlite`. `GroveError` is exported from the root module and extends `Error`. Reads and edits return synchronously or throw; the reader kernel does not run Effects. Effect schemas remain supported for validation. There is no `@tardie/grove/effect` entry point. The root module has no `JsonTree`, `Node`, `Metrics`, `StagedNodes`, `FORMAT_VERSION` or `REFERENCE_FORMAT_VERSION` exports. SQLite chunk decoding and raw node metadata are internal. Standalone persistence batches expose encoded text entries, and document references use Grove's codec. The synchronous store's documents expose `reference` directly; there is no public `documentReference` helper.

## Custom journals

Every `Journal` requires `storedValues: DocumentSession` backed by synchronous, colocated Grove storage. `storedSession(store)` adapts a synchronous Grove store to that surface. The journal must commit its logical records and the retained Grove dependencies in the same native transaction. Platform's `synchronousJournal` supplies this integration for a `SyncSqlite` driver. Asynchronous loaders cannot implement synchronous cold reads.

Checkpoint payloads are `Uint8Array` envelopes with a SHA-256 digest. `encodeCheckpoint`, `decodeCheckpoint` and `checkpointDigest` operate on bytes. There is no separate `treeCheckpoint` journal surface, `TreeCheckpoint` payload or `checkpointEncoder` export. `DocumentChanges.references` contains `{ name, reference }` entries under `EffectInputChanges.documents`. Durable checkpoint entries carry an optional `reference`; document state is `{ _tag: "DocumentState", reference }`. `DocumentSession` explicitly defines binding, synchronous reads, capture and local retention for both memory and SQLite adapters. Node staging and persistence acknowledgement belong to Grove. Version-2 byte envelopes remain subject to the checkpoint decoder's operation migration and current validation; this does not convert a legacy database layout or raw tree references.

Low-level standalone persistence uses `session.staging.prepare(references?)` to obtain a batch and `session.staging.acknowledge(batch)` after a successful native commit. `batch.nodes` contains the staged entries to write. Omitting references snapshots all staging. The `nodes`, `staged`, `persisted` and `committed` methods are absent. Integrated-store callers use `grove.commit` inside `grove.transaction`; the store handles acknowledgement. Discard abandons unheld staging and preserves dependencies of held drafts; release their holders to abandon those drafts.

Grove layout, read-cache and collection settings belong on the platform's `checkpointTree` options. Core's checkpoint policy accepts `everyEvents` and `maxBytes` as applicable. Native factories expose effective chunking and collection policies on the returned journal.

Native Bun journals honor file, WAL and busy-timeout options. They reject Effect SQL query-name transforms, result-name transforms and span attributes. `DEFAULT_BUN_BUSY_TIMEOUT_MS` is 5,000 milliseconds, `busyTimeout` overrides it, and `journal.sqlite` exposes the effective timeout and WAL configuration.

## Completed act results

Fulfilled act results at or above `DEFAULT_EFFECT_RESULT_COLD_MIN_BYTES`, 2 KiB, move to Grove when a stored-value session is available. `effectResult.coldMinBytes` configures this independently of `effectInput.digestMinBytes`. Reading `handle.result.status` does not materialize the result. Reading a fulfilled result's `value` synchronously loads it and validates the act's success schema. Repeated value reads can materialize it again; application code controls whether to retain the value it reads.

Checkpoint `maxBytes` includes referenced result payload sizes. Checkpoints retain cold results across restart, and inline results can acquire cold references during restoration. A historical digest-only result without stored payload bytes remains unavailable; this API cannot recreate discarded bytes.

## Recovery callbacks

Native scheduler and watchdog transaction callbacks must finish synchronously. SQL bookkeeping commits before storage flush and physical alarm synchronization. A flush or alarm failure can report an error after the durable commit; reopening restores the recorded wake, and retrying an append at its previous position conflicts. Delivery and recovery execution run outside the native transaction.
